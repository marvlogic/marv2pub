# Marv-2: parked status

Marv-2 is an experimental Racket-based tool for infrastructure as code (IaC)
and CI/CD.  Development is currently parked while the underlying language
design is considered further.  The repository remains useful as a record of
the design, its AWS and Docker experiments, and its test modules; it should
not be treated as a production-ready provisioning tool.

## What exists

- A declarative resource model with AWS EC2/S3 and Docker drivers.
- A planning/state layer that records resources, calculates create/update/
  replace/delete operations, and persists state plus its dependency graph.
- Resource references that add graph edges, so the plan can apply prerequisites
  before dependants.
- Docker-backed CI jobs in `modules/tests.rkt`, including dynamically generated
  unit and integration test jobs.
- Composition and iteration experiments: a resource-producing function can be
  assigned as a resource-like value, and `for/res` creates a collection of
  scoped resources.

## Language constructs

The DSL is implemented as Racket macros, rather than as a separate parser.
The following syntax is taken from the modules in this repository.

| Form | Meaning | Example |
| --- | --- | --- |
| `(:= name expression)` | Declare `name` in the current state context.  The value is registered in the plan under that resource ID. | `(:= aws aws-driver)` |
| `(:: driver type config ...)` | Build a resource declaration using `driver`.  It is normally nested in `:=` or `::=`. | `(:: marvd checkpoint (<= instance (rref instance instance-id)))` |
| `(::= name driver type config ...)` | Convenience form for `(:= name (:: driver type config ...))`. | `(::= sg aws aws-security-group (<= vpc-id (rref network vpc-id) ...))` |
| `(:> name := driver :: type key value ...)` | Compact resource declaration.  It expands into `:=`/`::` and builds the configuration hash from alternating keys and values. | `(:> bucket := aws :: aws-s3-bucket name "marv-2210" region "eu-west-1")` |
| `(<= key value ...)` | Build an immutable configuration hash.  Each assignment runs with attribute context, which makes reference diagnostics/dependency handling attribute-aware. | `(<= vpc-id (rref vpc vpc-id) cidr-block "10.0.2.0/24")` |
| `(mkih key value ...)` | A general hash-literal helper for configuration. | `(mkih network-acl-id (rref acl network-acl-id) protocol "17")` |
| `(rref resource attribute)` | Read an attribute from another declared resource.  Invoking that resource inside the declaration context records a dependency edge. | `(rref igw internet-gateway-id)` |
| `(:= name for/res clauses body ...)` | Declare resources generated by an iteration; the loop runs in a scoped resource context. | `(:= unit for/res ([(unit rkt) (in-hash unit-tests)]) ...)` |

For example, the network module declares a VPC, then uses its ID in a subnet:

```racket
(:> vpc := aws :: aws-vpc cidr-block "10.0.0.0/16")

(::= sn1 aws aws-subnet
     (<= vpc-id (rref vpc vpc-id)
         map-public-ip-on-launch #t
         cidr-block "10.0.2.0/24"))
```

The `rref` in `sn1` calls the VPC binding while `sn1` is being declared.  The
state context then records `sn1 -> vpc` in the graph; the reference itself
resolves to the requested value from the VPC's configuration/state.

## Known unfinished areas

- Driver lifecycle handling is explicitly unfinished.
- Replacing a resource with the same ID but a different type is unimplemented.
- Failed deletions can leave state and replacement bookkeeping inconsistent.
- The EC2 composition example notes an unresolved deletion-order problem for
  security groups and instances.
- Stateful-variable lifecycle updates in the Docker test module are still
  marked TODO.

## Resume notes

Start by reading the runnable declarations in `modules/aws-networks.rkt`,
`modules/aws-ec2.rkt`, `modules/aws-s3.rkt`, and `modules/tests.rkt`.  The
macro definitions are in `state.rkt`; `stx-utils.rkt` provides `mkih` and
`rref`.  Any restart should first decide whether this macro surface remains
the desired language, then address lifecycle and graph/deletion semantics
before expanding provider support.

## Installation & Usage
```bash
# Dependencies (if using shell)
./deps.sh # if available

# Install package for development
raco pkg install --name marv --link `pwd`

# Run tests
racket modules/tests.rkt
```

### AWS service models

`aws/ec2/service-2.json` and `aws/s3/service-2.json` are generated AWS API
service descriptions sourced from the [botocore repository](https://github.com/boto/botocore),
not hand-maintained project files.  Obtain the versions appropriate to the
chosen botocore revision from:

```text
botocore/data/ec2/2016-11-15/service-2.json
botocore/data/s3/2006-03-01/service-2.json
```

For example, from the repository root (pin `<botocore-revision>` when
reproducibility matters):

```bash
curl -L https://raw.githubusercontent.com/boto/botocore/<botocore-revision>/botocore/data/ec2/2016-11-15/service-2.json \
  -o aws/ec2/service-2.json
curl -L https://raw.githubusercontent.com/boto/botocore/<botocore-revision>/botocore/data/s3/2006-03-01/service-2.json \
  -o aws/s3/service-2.json
```

Use the uncompressed `service-2.json` files: this code reads JSON directly
and does not decompress botocore's optional `.json.gz` distribution files.
